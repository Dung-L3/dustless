## What and why

The red list was matched lexically (`isRed`, `node:path` resolve, never `fs.realpath`). A path that reaches a red directory through a symlinked component — `~/projs/portal/canary.txt` where `portal` points at `~/Documents` — is lexically innocent, so `apply --yes` deleted the real file inside `~/Documents` and `largefiles --delete` trashed it. This is a data-loss path of exactly the kind the red list exists to stop.

This PR adds `isRedReal` (`src/core/paths.ts`), which resolves `realpathSync` and is used at all three delete guards:

- `refusal` (`src/core/apply.ts`)
- `deleteLargeFile` (`src/core/largefiles/index.ts`)
- `assertPathDeletable` (`src/mcp/safety.ts`)

Fail-closed: `isRedReal` answers `false` when the path cannot be resolved at all (a path that cannot be resolved cannot be deleted either); resolution changes the answer only when the path exists and points somewhere else. Deleting a symlink itself still merely unlinks it.

Adversarial coverage: `tests/e2e/redlist-realpath.test.ts` (6 cases, red-neutral symlink names so no lexical match can mask the result).

Still open, reported not fixed here: `scan` filters candidates lexically (`isRed` in `src/core/scan.ts`), so a symlinked path inside a red directory can still be counted as reclaimable although it is no longer deletable. Tracked as Q5.
