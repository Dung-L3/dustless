# Decisions

The source files used to carry these facts as comments; the comments are gone and a project rule forbids new ones, so the knowledge lives here instead. Every entry below records something non-obvious that a comment was protecting: a measurement, a failure mode, or a reason the obvious-looking change breaks something. Changing any of them needs a measurement to justify it — most of them exist because someone measured the failure first.

## Menu bar

1. `MenuBarExtra` uses `.window` style, not `.menu` (DustlessApp): the popover carries measurements, not a list of commands. A `.window` popover only closes on a real click outside, so every row that navigates must dismiss itself — the old `.menu` closed the moment an item was picked.
2. `leave()` uses the environment `dismiss()` (MenuBarContent.leave): ordering the panel out or closing its window directly hides it without telling SwiftUI, whose is-presented flag then still reads open — the next status-item click does nothing and the one after reopens. Measured on the built bundle, both ways.
3. `.task` fires once per popover lifetime, not per open (MenuBarContent): a `.window` popover keeps its content view alive across open/close, so appearing is not an "opened" event. Live reads re-trigger on `NSWindow.didBecomeKeyNotification` for any window that is not the main window; every read behind `refreshLive` is throttled, so key-window churn costs nothing.
4. The popover dismisses on `router.module` change (MenuBarContent.onChange): the Go menu's ⌘1–⌘5 fire while the popover is open and would leave it floating over the module it just opened. Dismissing a popover that is not presented is a no-op, which keeps the window's own ⌘1–⌘5 harmless.
5. The popover binds no key equivalents of its own (MenuBarContent footer): the old menu bound a bare `q` and swallowed keystrokes. The ⌘1–⌘5 the rows display belong to the window's Go menu, and the row text is derived from `Module.shortcut` itself — never a parallel map, which is exactly the copy that drifts.
6. Popover appearance comes from `NSApp.appearance` (AppSettings.applyAppearance): the menu-bar popover is AppKit's surface, outside every SwiftUI scene, which is the one place a scene-level `.preferredColorScheme` never reached. Measured with a live flip: under `NSApp.appearance` windows report `appearance == nil` with an inherited `effectiveAppearance`, so windows and sheets created after the switch are already correct without re-applying. It is applied in `AppSettings.init`, before any window exists — a stored Dark otherwise opens in the system's appearance for a frame.
7. Opening the popover reads only cheap state (MenuBarContent.refreshLive: `ensureMemory`, `refreshIfStale`, `fetchStorage`) — never a rescan: a full disk walk is what the Scan button is for, and merely opening the menu must not start one.
8. The menu-bar mark is a template `NSImage` at 18pt (DustlessApp.MenuBarIcon): macOS uses only its alpha channel, so `MenuBarIcon.png` must keep a transparent background — an opaque one painted a solid square in the menu bar when it shipped (guarded by tests/menubar-icon.test.ts).

## Window and panels

9. ⌘R is registered once, in the File-menu command group (DustlessApp.commands), and nowhere else: `SummaryHeader` used to register the same shortcut with a different disable rule, so which one answered depended on the open module, and in Cleanup the two disagreed. `TierTab` likewise carries no ⌘1–⌘2–⌘3 — the Go menu owns those keys.
10. No `.id` on the module switch (ModuleContent): the `switch` already builds a fresh module on every change; measured, the incoming module's body ran twice per switch with the id and once without. State lifetime and the cross-fade are unaffected either way.
11. No `.layoutPriority` on the content band (PanelScaffold): it buys the content its leftover height by compressing the bands above — measured, the AirDrop note capped at two lines rendered one. Bound the paragraphs instead.
12. Every pinned sentence is capped at two lines (NetView.errorLabel and siblings): uncapped, the refresh banner and the AirDrop error alone cost the operations list 77pt — three of its five rows — at the smallest pane the window allows. `.help` alone is not enough: a truncated `Text` labels itself with the truncated string, so the full sentence goes to the hover *and* the `accessibilityLabel`.
13. The AirDrop note is capped at two lines (NetView.airDrop): the sentence is ~200 characters in every language; measured cost to the list was 39pt, about one operation row.
14. The operations band stays pinned above the list at a measured cost of 34pt (NetView.operations): moving it into the scroll put its first 2 of 26 points in the viewport at the smallest pane — pinned and capped is the cheaper option.
15. `PanelStateView.messageLabel` applies `lineLimit` *after* `fixedSize(vertical:)`: `fixedSize` hands the text an unbounded height proposal and would otherwise win. Measured at 440pt with this chain: one line is 14pt, two are 28, six are 84 — the cap binds. Six lines because a Rust panic backtrace is 344 characters ≈ nine lines ≈ 126pt of a pane that had less to spare; the hover and text selection still carry the whole sentence.
16. Panels own their search field (WindowChrome.SearchField), never `.searchable`: `.searchable` attaches to the window toolbar, so the field appeared beside the sidebar and a query was lost on every module switch. The findings query lives in `ScanStore.findingsQuery`, which outlives the detail pane's rebuilds.
17. One `.sheet(item:)` binding for every Storage dialog (StorageSheet): four separate sheet bindings let an action that finished a job set its result while clearing its confirmation in the same update — SwiftUI tried to present one sheet while dismissing another and the window locked up.
18. An alert cannot present on top of a sheet (StorageView.fail/presentNext): the error is queued in `nextAlert`, the sheet dismissed, and the alert raised after a 260ms settle delay for the dismissal animation; presenting during the dismissal wedges SwiftUI the same way.
19. `actionErrorPresented` is a real Binding, not `.constant` (StorageView): a constant cannot be written back, so the alert's own dismissal never reached the state and the alert re-presented over the next sheet with nothing to report.
20. A failed read keeps the last report on screen (ScanStore.rescan, the module states in ModuleContent, NetView): stale numbers with an error banner beat a blank panel. A failed rescan also keeps the selection and — when a report exists — the engine handle; otherwise the list is readable but unactionable.
21. Module data lives in ScanStore behind staleness windows — `ensureMemory`/`ensureStorage*` 45s, `refreshIfStale` 15s: a module switch is not a reason to re-read the process table or the app list. The retry buttons and post-action paths call the `fetch…` variants directly, which bypass the window. The storage inventory and findings query live in the store because the views are rebuilt on every module switch and `@State` used to throw them away.
22. AutoCloseGate is depth-counted (DustlessApp): the macOS authorization dialog is owned by another process (SecurityAgent), makes the app inactive and takes key status without ever attaching a sheet, so SwiftUI reads it as a click-away and would bring the window forward while the user is typing a password. `end()` re-activates and refocuses the pending window only if it is still visible — a cancelled prompt must not be resurrected by its own release. Only an advanced net operation without the sudo rule is gated (NetControl.run); a safe operation never leaves the app.
23. AppRouter.select brings the window forward only when it is not already key: the sidebar selects on every click, and re-activating a key window pulls focus out of the search field the user is typing in.
24. Reduce Motion keeps fades and drops scale (MemoryView.statusView, DetailView.fadeInFindings, OverviewView.countUp, ModuleContent): the fade is the signal that a row changed; a scaling element is exactly what the setting is about. The findings fade is opacity-only and under 200ms — a slide would imply the rows scrolled away on their own.
25. A missing report renders `—`, never `0 B` (SummaryHeader): "Reclaimable 0 B" above "Nothing scanned yet" reads as a measurement; a real zero after a scan is still a real zero, so the dash is only ever the missing report.
26. Byte columns are fixed-width (`PanelStyle.byteColumnWidth = 68`, the sidebar tier rows): a column that sizes to its widest row makes the numbers beside it jump sideways every time a value changes width. Engine errors are shown verbatim in a monospaced font — when the engine explains a refusal, its wording beats anything the UI could paraphrase it with.
27. Alert and result wording is stored as keys, never rendered text (`StorageResult.titleKey`, `nextAlert`, `L10nText`): an alert can sit on screen across a language switch, and text rendered when the failure happened is the one string that keeps speaking the old language.

## Storage

28. The volume strip is horizontal, not a column (StorageView.volumeStrip): measured at 640×560, a column cost the inventory 360pt with one volume, 248pt with three, 136pt with five and *all of it* with eight — a Mac with a few external and network mounts showed an empty Storage pane. The volume count is data the user controls; it may not decide the layout.
29. VolumeCard width is 260, not 210 (VolumeCard.width): at 210 the inner box is 186pt and the caption of an ordinary 500 GB SSD — "294.9 GB used · 106.7 GB free of 401.6 GB", 214pt — lost the total. 260 fits the widest real triple in English (214pt) and Chinese (228pt); Vietnamese wants 278pt and still truncates its tail, which the hover and spoken label carry.
30. VolumeCard height is fixed and measured at 48.00pt (34-character name, longest `ByteFormat` caption, empty name): every child is `lineLimit(1)`, so only the width is a decision. The empty strip is really free: an empty `HStack` in a horizontal scroll view measures 0.00pt — a scroll view wrapping a bare `EmptyView` measures 10pt, so do not "simplify" the stack away.
31. Result cards are capped at 160pt (StorageView.inventory, CleanupResultCard.disclosure): one app can report dozens of leftover paths, and a report that grows the window is worse than a report you scroll. The per-outcome rows start folded for the same reason.
32. Each Storage tab keeps its own query (StorageView.searchBinding): typing in Files must not silently reset what Apps was showing.
33. The large-files walk starts only when the Files tab is opened (StorageView.onChange(of: section)): walking the home directory is slower than reading an app list, so it waits until the tab is actually opened.
34. An uninstalled app leaves the list immediately (ScanStore.removeStorageApp, StorageView.performUninstall): a slow or failed refresh must not leave a deleted bundle sitting in the inventory. A purge also re-reads the volume strip — it frees real space on the volume it lived on; a trashed large file does not re-walk, because the report is already on screen.
35. A bundle id is validated before any path is derived from it (`isSafeBundleId`, src/core/apps/index.ts): `join()` collapses `..`, so a crafted `CFBundleIdentifier` of `../../../victim` pointed every leftover template outside HOME, and `--purge` made that a permanent `rm -rf` of whatever it pointed at. Each related path is checked twice — resolves strictly inside HOME, and is exactly one of this bundle id's own template expansions — and an uninstall with an unsafe id is refused whole rather than removing the bundle and leaving unknown leftovers behind.
36. App-uninstall refusals are outcomes, not exceptions (engine contract): not a `.app`, a system app, outside the allowed app directories, a denied path, an unreadable or unsafe bundle id — all come back as a `failed` outcome in the report; nothing silently falls back to the Trash. The purge flow always sends `--purge`, and the confirmation says "permanently deleted"; without the flag the engine moves to the Trash, which is a different promise than the one the sheet makes.

## Memory

37. The process list is grouped by app bundle with a cap of 15 groups, applied after filtering (MemoryView.groupLimit, filteredGroups): the cap is on apps, not processes, so a group is never shown with half its memory missing, and a category filter surfaces the biggest members of that category. The count line states when the filter matched more than the cap draws.
38. The bundle is found via the `.app/Contents/` marker (ProcessGroup.bundlePath): it survives spaces in the application name, and keeps `.apple`, `.xpc` and an argument such as `--out=/tmp/report.app` from passing as bundles. The outermost bundle wins (Brave's twelve renderers are one group); `ppid` is deliberately ignored — the process tree reshuffles on every respawn, a bundle does not. Equal totals break on the group key so the same report always draws the same order.
39. Process icons are memoised per bundle path (MemoryView.iconCache): `NSWorkspace.icon` reads the icon file off disk on every ask, and this runs inside `body`, which re-runs on every hover and every keystroke. Past 400 entries the cache is dropped wholesale — a Mac has a few hundred bundles at most.
40. `isStopping` is set on the main actor *before* the Task body (MemoryView.killProcess): a second click in the same run loop still saw `false`, so a double-click started two kills of the same pid and the engine answered the second with "no such process".
41. Search matches helper process names and exact pids, not just app labels (ProcessGroup.matches): the thing eating the memory is often a helper ("Renderer"), and hiding its group hides the twelve helpers that make the app heavy. A pid is an exact identifier — 42 is not 4242.

## Network

42. `serviceFor` returns `""` when the device is not in the hardware-port list (src/core/net/inspect.ts): `networksetup` is addressed by *service* name and rejects a device ("en7" is not a recognized network service); the old fallback handed the device back anyway and `--print-privilege` emitted a sudoers rule naming a command the OS rejects every time. `-listnetworkserviceorder` is the second device→service mapping and knows VPN, Thunderbolt Bridge and some USB entries; it is consulted when the first misses. An unresolved service is a reason to refuse, not to guess.
43. DNS servers are deduplicated across resolver blocks (inspectMac): `scutil --dns` prints one block per resolver and repeats the same nameservers; the user has a list of servers, not a list of query scopes.
44. Interface-touching operations run with `--force` (NetControl.run): the engine refuses them while the interface is the machine's only route — exactly the situation the user opened the panel to fix — and the admin prompt is the consent.
45. There is no unprivileged fallback for an advanced operation (`execute` in src/core/net/index.ts): root runs the step directly; otherwise it goes through `sudo -n <absolute path>` — `-n` fails loudly instead of blocking on a password prompt the caller cannot answer. A half-applied network change is worse than a clean refusal.
46. sudo's "password is required", "a terminal is required" and "not allowed to execute" all mean missing consent, not a broken command (the `needsConsent` regex, in both net and awdl): "not allowed to execute" is what sudo says when a rule exists but no longer matches (a different interface, a renamed service). All three become `refused` with the install hint, not `failed` with sudo's own sentence.
47. Sudoers arguments containing `"`, `#`, `*`, `?`, `[`, `]`, `\` or newlines are refused, never escaped (sudoersArg): they are sudoers wildcards or comment starters — a rule containing one matches a whole family of commands instead of the one exact command the file exists to allow. A service name with spaces ("USB 10/100/1000 LAN") is double-quoted, which is what makes the rule match the single argv element the engine passes.
48. The macOS root commands are absolute paths (`MAC_COMMANDS`) and the privilege rule is derived from `buildSteps` (netPrivilegeSteps), never written out a second time: a sudoers rule has to name an absolute path, the engine must invoke exactly the paths the rule names, and the rule cannot drift from what is actually run.
49. The sudoers file names contain no dot (`/etc/sudoers.d/dustless-net`, `dustless-awdl`): sudo ignores a sudoers.d file whose name contains one. `visudo -cf` validates the staged copy *before* it is installed — installing first and validating second could leave a malformed file in /etc/sudoers.d, which sudo reads, and wedge sudo machine-wide.
50. Every decision about the rule reads the file off disk (NetControl.readPrivilegeInstalled), never the published copy: the published value is a snapshot, and deciding on a stale one is how two SecurityAgent prompts stack up. The install result is also re-read from disk before success is decided — reading the published property inside the `do` still saw the pre-install value, so a perfectly good install reported itself a failure.
51. The engine refuses `flush-routing` on macOS by design (`route flush` would drop the default route), so the app's `NetOp` list omits it entirely (DustlessKit/Model/Net.swift); it stays on the CLI for the Linux side.
52. A state read is `net --advanced --json` with no named operation (DustlessCLI.net): a bare `net` flushes the DNS cache, which is not what a state read should do.
53. `netExitCode` maps refused/failed outcomes to exit 1: a script has to tell "did nothing" from "did the thing", and only the exit status carries that; the report says why.
54. Run buttons disable on `privilegeBusy` as well as their own run (NetView.runButton): no operation waits on the install/remove admin prompt, but a second SecurityAgent dialog stacked on it is one the user cannot answer.
55. NetControl forwards `awdl.objectWillChange` (NetControl.init), and AwdlControl is a shared singleton: the panel observes NetControl, not the AirDrop control — without the forwarding a freshly installed permission would not turn the install button into the installed fact until a reopen. Menu bar, Settings and the Network panel all drive the same live AWDL state.
56. The AWDL rule permits exactly two `ifconfig awdl0` commands and nothing else; a wildcard would widen what the password-free toggle may run. A missing interface and a present-but-down one are told apart by ifconfig's exit ("does not exist" → `absent`): both read as "off" in the status line, but only one can be toggled.

## Engine / CLI

57. `apply` re-scans on its own, so the selection must travel with the command (`--only-file`; DustlessCLI.apply and readSelection in src/cli.ts): the exact resolved paths are written to a temp JSON file and the engine skips any finding outside the set — without it, ticking one row deletes every green/yellow finding the fresh scan happens to find. The set only ever narrows: red and blocked findings stay refused inside it. The file names the user's own paths, so one `defer` removes it on throw, timeout and cancellation. Callers must pass a non-empty list.
58. The engine prints a full JSON report and *then* exits 1 whenever an outcome failed or was refused (`apply`, `ram --kill`, `apps --uninstall`, `largefiles --delete`): a non-zero status is not by itself a failure — decode first, and fall back to the exit status only when no JSON reads (DustlessCLI.decode). `runAsRoot` appends `|| true` for the same reason: osascript turns a non-zero exit into an error that throws the report away, and the report is the answer.
59. Under `--json`, an argument or validation error is `{"error":"…"}` on stdout, exit 1, nothing on stderr (`fail()` in src/cli.ts): the decoder surfaces that message instead of a bare exit status. Otherwise errors go to stderr and `--quiet` never suppresses them — a quiet run that exits 1 with no message is the worst outcome there is. A zero exit with unreadable JSON prefers stderr's sentence (a missing tool, a denied prompt) over a decoding error nobody can act on.
60. stdout must be drained before exit (flushStdout in src/cli.ts, writeOut in src/core/output.ts): when stdout is a pipe (MCP clients, agents, `| jq`, the macOS app), Bun can hand fd 1 to the kernel non-blocking and the pipe buffer holds 64 KiB — a large report's tail was dropped on exit, exactly 65536 bytes, so `ram --json | cat` produced invalid JSON while `> file` looked fine. Write 16 KiB chunks and wait for each to be accepted.
61. An option value that starts with `--` is a missing value (src/core/args.ts `opt()`): `apps --uninstall --confirm` used to pass `"--confirm"` as the app path, and `largefiles --delete --json` reported on a file named `--json`.
62. An unknown flag is refused before anything runs (unknownFlag in src/cli.ts): a typo used to be harmless-looking and then perform a real action — `net --bogus` ran the default DNS flush.
63. `--help` wins for every command (src/cli.ts main): `scan --help` used to run a full scan.
64. `doctor` computes the Full Disk Access verdict before the `--json` branch and exits 1 on it: otherwise `doctor --json` and `doctor` disagree about the same machine. The verdict is EPERM/EACCES on `~/Library/Mail`; the failure line goes to stderr and is never taken away by `--quiet`.
65. `sysctl vm.swapusage` prints fractional values; byte counts are rounded to integers (parseSize in src/core/ram/index.ts): the JSON contract feeds strict decoders that reject 5368709.12.
66. Kill guards (killProcess in src/core/ram/index.ts): refuse PID 1, the engine's own pid, the parent shell, `kernel_task`/`launchd`/`WindowServer`/`loginwindow`, root-owned processes without `--force`, Dustless itself, and anything under 50 MiB (`MIN_RECLAIMABLE_BYTES` — killing it would not help). Without `--confirm` the run is a dry run that reports reclaimable; `reclaimed` is the measured memory delta, before vs after.
67. The large-files walk is bounded-concurrency (src/core/largefiles walk, `WALKERS = 32`). It was serial, and `--limit` never made it cheaper because the limit is a slice applied *after* the walk. Measured over a real home: 24.7 s serial, 10.5 s at 32 workers, with the same 38 files reported before and after. The count is not a cliff on this machine — 8 workers is 11.5 s, 16 is 10.9 s, 64 is 11.3 s — so 32 is a comfortable minimum rather than a discovered knee. Two things to keep: the pool only engages because the root directory is expanded *before* the workers start (seeding the stack with `[root]` alone makes every worker but one find it empty and return, which measured 25.8 s — slower than serial); and a worker exiting while another is mid-`readdir` loses nothing, because the worker that pushes a directory goes on to drain its own pushes. An earlier version of this entry claimed eight walkers measured ten times slower; that does not reproduce at 11.5 s, and the notes are kept here rather than deleted because the discrepancy is the useful part.
68. The large-files walk only ever enters the home directory (scannedRoots): that one rule keeps `/System`, `/Library`, `/Applications` and every other volume out, instead of a deny list needing one entry per new system directory. It skips `.git` (repository history, not junk — trashing a pack corrupts the repo) and `.Trash` (already reclaimed; listing it would offer to trash the same bytes twice), and skips symlinks (a symlink is not the bytes it points at). Everything else — Documents, Library — is walked on purpose, and `--delete` refuses red-listed paths by name, the same list `scan` uses: listing is harmless, deleting mail or git objects is not.
69. `remove` retries only on Windows — 4 attempts, 200ms·2^n backoff, only for EBUSY/EPERM/EACCES/ENOTEMPTY (src/core/apply.ts): a read-only child surfaces as ENOTEMPTY on the parent directory on macOS and as EACCES/EPERM on Linux.
70. Deletion is refused for red-listed paths, HOME, any parent of HOME and the filesystem root (refusal in src/core/apply.ts); the MCP layer repeats the same guards independently. A busy native command (npm/pnpm/yarn running) skips its caches rather than corrupt a live process.
71. A scan never pre-selects anything (`ScanReport.initialSelection` is `[]`): the engine fails closed and the UI must too — the user opts in to each path.
72. MCP `apply` is all-or-nothing and refuses by default (src/mcp/safety.ts): `confirm` must be exactly true, and unknown rule ids, wrong tier, red paths, blocked findings or a batch over 50 GB (without `allow_large`) each refuse the whole call with every problem listed. `guardStdout` redirects every console method to stderr so a stray log cannot corrupt the JSON-RPC stream on stdout.
73. The engine deadline is scheduled off the serial dispatch queue (DustlessCLI.run): that queue then blocks in `readers.wait()`/`waitUntilExit()` until the child is gone, so a timer scheduled on it could never fire and a hung engine would hang the app forever. A terminated engine gets SIGTERM, then SIGKILL after a 2s grace (`RunningProcess.killGrace`).

## Tests

74. The e2e harness builds the compiled binary on import if it is missing (tests/e2e/harness.ts): the suite must not depend on CI's step order or on which test file the runner loads first — that missing guarantee made the deep-tree and concurrent-scan tests fail on the macOS and Windows runners.
75. Every e2e case drives the compiled binary in a child process whose HOME is an mkdtemp sandbox (harness `sandbox`/`assertTempRoot`): setting `process.env.HOME` would not move `os.homedir()` for the engine, and a wrong home means a real file leaves the build. Paths outside the temp root, and anything under the real home, are refused by the harness itself before the binary runs.
76. The pipe test must be drained by a blocking reader (`cat`) to reproduce the 64 KiB truncation (tests/e2e/pipe.test.ts): a Node stream reads fast enough to hide the race. `cat` is POSIX, so the test is skipped on Windows.
77. The i18n test parses `Localization.swift` directly (tests/i18n.test.ts): the three Swift tables are the single source of the app's wording, and the languages are taken from `Lang.allCases` so adding a language extends the test instead of being silently skipped. A duplicate key is silent data loss — Swift keeps the last literal.
78. The menu-bar icon test decodes the PNG and asserts the background is transparent (tests/menubar-icon.test.ts): the mark is a template image, macOS uses only its alpha channel, and an opaque background is exactly what shipped once.
79. Engine fixtures are captured from the real engine and pinned (scripts/capture-engine-payloads.ts): mtimes and ages are rewritten to constants so the Swift contract tests — decode the real payload, decode a report printed then `exit 1`, the selection file removed when the run fails, the `{"error":…}` payload becoming the message — stay deterministic.
80. The e2e unknown-flag sweep excludes `mcp` on purpose (tests/e2e/args.test.ts): a validation bug there would start a stdio server and hang the suite instead of failing a test.

90. The process name was the first space-delimited token of the ps command (parsePsLine in src/core/ram/index.ts, `executablePath` in Sources/DustlessKit/Model/Memory.swift): a path with a space ("/Applications/Brave Browser.app/Contents/MacOS/Brave Browser Helper") yielded the name "Brave", so helper rows whose bundle path carried the app's label looked like they belonged to a bare "Brave" executable, and the Memory panel's name search (Decision 41) never matched "Brave Browser Helper (Renderer)". A process in the Swift contract suite failed on both origin/main and the v2 branch, captured in a baseline log from that run (`aGroupIsFoundByAHelperProcessNameToo`: name "Brave", `matches("(renderer)")` false) — that observation is the evidence; the failing fixture reproduced the shipped engine output exactly, so the assertion was a product finding, not stale test data. The name now comes from `.app/Contents/MacOS/` or `.app/Contents/Resources/` when present (the file after it, cut at the first whitespace-dash argument boundary); otherwise the text before the first ` --`; otherwise the first token, or — when the command is a path — the text before the first token containing no `/`, which never splits a space inside the path. The known ceiling: an argument boundary inside the binary's own name is still ambiguous in the ps command string; the boundary heuristics err on the side of merging into the path. The engine keeps emitting the same JSON shape (no field added or renamed), so src/types.ts and the captured payloads were untouched; the Swift mirror helper in `process()` now derives names with the same rule so it keeps reproducing what the engine actually emits.

## Packaging

81. The macOS bundle is ad-hoc signed and verified (`codesign --force --deep --sign -` then `codesign --verify`, scripts/bundle-macos.ts), and the generated Info.plist must pass `plutil -lint`. The compiled engine binary is signed at build time on macOS (scripts/build.ts).
82. The DMG self-checks by mounting (scripts/make-dmg.ts): the built image is attached read-only and the build fails unless both Dustless.app and the Applications symlink are present in the mount.
83. The Windows build asserts it is self-contained (scripts/package-win.ts): `file` must report PE32+, and `strings` is scanned for bun/node/libuv/libnode/vcruntime/msvcp DLL imports — any external runtime dependency fails the package.
84. icons.ts needs macOS (qlmanage, sips, iconutil) and exits elsewhere; committed icons live in `brand/generated/`. `MenuBarIcon.png` is committed under `apps/dustless-mac/Assets` and copied into the bundle — the bundle build fails without it.

## Source layout

85. `src/cli.ts` is a thin dispatcher only; each command lives in `src/cli/`. The grouping follows which commands share code rather than alphabetical order: `scan.ts` holds scan and apply because apply re-scans and the `--only-file` selection travels with it (entry 57), `net.ts` holds net and awdl because both build sudoers privilege rules from the same `validSudoersUser`/`netPrivilege` helpers, `storage.ts` holds apps and largefiles because both print an `UninstallReport` through the same `printUninstall`. `rule.ts` and `doctor.ts` stay separate: they share nothing but `loadRules()`. `context.ts` parses `process.argv` once at module load and exports `flag`/`opt`/`fail`/`unknownFlag`/`flushStdout`; `cli.ts` must import it before any command module reads a flag, because the parse has to run before `main()` — a module that moved the parse later would make `unknownFlag` (entry 62) and the `--help`-wins check (entry 63) see the wrong argv.
86. There is exactly one way to build the app bundle: `bun run bundle:mac` (`scripts/bundle-macos.ts`). `apps/dustless-mac/scripts/bundle.sh` was a second, older path, and it had drifted in ways that misled people rather than merely annoying them: it copied neither `Dustless.icns` nor the menu-bar mark, its `Info.plist` had no `CFBundleIconFile`, it treated a failed `codesign` as a warning, and it wrote its output to `apps/dustless-mac/build/` where nothing else looks. The in-app strings that told users to run it now name `bun run bundle:mac`.
87. Documentation references a **file and a symbol**, never `path:line`. Line numbers rot the moment a file is touched, and this repo has already paid for that twice: every `src/cli.ts:<n>` reference in the three READMEs was invalidated by the split in entry 85 in a single commit. When a reference must be precise, name the function or the constant.

91. Red-list matching normalises the path before the pattern test (`isRed` in src/core/paths.ts): duplicate separators collapse to one, backslashes become `/`, and a trailing separator is dropped, so `~/Mail/`, `~/Mail//` and `~/Library//Application Support//com.apple.Photos` are all red. The patterns stay substring-anchored on purpose, which makes the list over-protective — `~/DocumentsBackup` is red too. 121. The AWDL sudoers rule is built from an allowlisted, fixed executable, and the environment seam that used to pick it is gone. `awdlPrivilege` (`src/core/net/awdl.ts`) interpolated `IFCONFIG` into the rule text and `IFCONFIG` was `process.env["DUSTLESS_IFCONFIG"] || "/sbin/ifconfig"`, so a newline in that variable produced a second, syntactically valid sudoers line: `DUSTLESS_IFCONFIG=$'/tmp/evil\nmac ALL=(root) NOPASSWD: /bin/sh\n#'` made `--print-privilege` emit a rule that `visudo -cf` parsed as OK and that granted a passwordless root shell — and the macOS app writes that text verbatim into `/etc/sudoers.d/dustless-awdl` as root (`AwdlControl.installPrivilege`), so the hole was permanent rather than a one-shot prompt. `visudo -cf` only checks syntax, so it was never the control that should have caught this. The rule now goes through one shared validator (`src/core/net/privilege.ts`): `sudoersRule` assembles the line and checks the account name and every command, `sudoersArg` refuses a newline, a carriage return, a NUL, `"`, `#`, `*`, `?`, `[`, `]`, `\` and `; | & $ > < ( ) { } ! ' \``, and `sudoersPath` adds the checks that matter for an executable — absolute path, no whitespace inside it, and membership in an allowlist that for AWDL holds exactly `/sbin/ifconfig`. The same character set now also refuses a `,` in a net service name, which the old `sudoersArg` let through: an unquoted comma splits a sudoers command list, so a service named `Wi-Fi,rm` could have added a second command to the net rule. `IFCONFIG` is the constant `/sbin/ifconfig`, and `awdlPrivilege` takes the executable it names as a parameter precisely so that the rule goes through `sudoersPath` instead of around it — the parameter's only accepted value is the allowlisted one. The executable the engine *runs* is a separate injected parameter with that same default (`AwdlOptions.ifconfig`), so a test can point it at a sandbox fake while no environment variable can steer production — the e2e reaches the fake through the fake `sudo` instead (entry 96), and every compiled-binary case runs with a hostile `DUSTLESS_IFCONFIG` in its environment to prove the binary ignores it. The app re-checks the payload before it installs anything as root (`isExpectedRule` in `AwdlControl.swift`): the destination path, the two expected commands, a plain account name, and the rule text must be exactly what those produce, so a hostile or buggy engine payload is refused instead of installed — the trust boundary the threat model's section 5 still lists as open. Tests: `tests/awdl.test.ts` refuses 29 hostile executable values (newline, carriage return, NUL, whitespace, every shell metacharacter, a relative path, a path outside the allowlist) and pins the exact rule; the validator is load-bearing — commenting out the `sudoersPath` call in `awdlPrivilege` turns that case red — and the file also asserts that no source file under `src/` names the removed variable; `tests/e2e/awdl.test.ts` asserts that the compiled binary contains no `DUSTLESS_IFCONFIG` string and that the printed rule and the escalated command stay the fixed ones while the hostile variable is set; `tests/net.test.ts` covers the widened refusal set for the net rule. Ceiling, recorded and not closed: the net rule still names the interface and service resolved at install time, and the app's net path (`NetControl.installPrivilege`) still installs whatever rule the engine prints, without the AWDL-side re-check — the same re-check belongs there and is not part of this change.

101. The rule format gained five optional fields and one that the shipped set is required to carry. `recoveryLabel` (`download` or `rebuild`) states the cost of re-creating what a rule deletes, and it is REQUIRED for every rule in the bundled `default-rules.yaml` (all 26 carry one; `loadRules` passes `requireRecovery` when normalizing the bundle) while a user file's rule without one still loads, because refusing to load a user file would silently drop rules from the scan, which is the fail-closed direction but also the silent direction — the value is validated whenever it is present, and `rule add` refuses to create a rule without it, so the only way to have a label-less rule is to write one by hand. `rule add` therefore takes the label as its fourth positional argument (`rule add <id> <tier> <desc> <download|rebuild> <path>...`), which changed an existing e2e call and is locked by a new case that a label-less add exits 1 with nothing on stdout. The other four fields — `busyProcesses` (non-empty list of non-empty names), `staleDays` (integer >= 1), `gitClean` (boolean) and `nativeCommand` (string) — are validated only when present, and `nativeCommand` is refused when its first token contains a path separator or the value contains any of `; | & $ > <` or a backtick: it is later executed instead of `rm`, so a rule file must not be able to smuggle a shell command. The schema and every refusal it adds are covered by tests/rules-schema.test.ts and the e2e `rule add` case; the measured pass counts for this change are in the commit history for that change.

Reason codes are `absent` (ENOENT), `no_access` (EACCES/EPERM), `not_supported` (no path for this platform) and `error` (anything else); a rule with at least one scannable path and no findings is not unscannable, and unscannable rules contribute nothing to `totals`, `reclaimable` or `freed`, so the new field can only ever add information, never a number. Deletion guards now judge the real path, not only its spelling. `realGuard` (`src/core/paths.ts`) returns `red`, `unresolvable`, `protected` or `symlinked` in addition to the resolved target: `protected` covers the resolved HOME, every ancestor of HOME and the filesystem root; `symlinked` covers any path reached through a symlinked directory component. A missing path verifies its parent's real path, so `link/missing` where `link` points into HOME or a red directory is refused by the guard instead of reported as a plain `{ real }`; a dangling parent symlink is `symlinked`, and any other parent resolution failure is `unresolvable`. The `ApplyOutcome.path` is the resolved target that was actually deleted, not the caller's raw spelling. macOS `/private/{var,tmp,etc}` aliases are canonicalised and Windows targets are lowercased before the comparison, so an ordinary `$TMPDIR` spelling is not mistaken for a link. The guard is used by `remove` in `src/core/apply.ts`, by `moveToTrash`/`purgePath` in `src/core/apps/index.ts`, by `deleteLargeFile` and by `assertPathDeletable` in `src/mcp/safety.ts`; MCP now distinguishes red, protected and symlinked refusals instead of calling every refusal a red-list match, and `deleteLargeFile` passes the actual refusal through instead of always saying `unresolvable`. The busy-process gate is still a name-only probe after a re-audit, and that ceiling is deliberate. `runningCommands` (`src/core/apply.ts`) lists `ps -Ao comm=` or `tasklist`, normalises each entry to an executable name, and `run` compares those names with the rule's `busyProcesses` or the `nativeCommand`/`BUSY_NAMES` fallback. A tool can therefore be invisible under its own name: on Windows npm and npx appear as `node.exe`; on macOS/Linux npm rewrites its process title to `npm …` and npx to `npm exec …`, `ps` reports that title in both `comm` and `args`, and `processName` does not split it, so neither the declared name `npm` nor the interpreter name `node` matches. pnpm usually runs as `node` (`pnpm.cjs`), Gradle's daemon as `java` (`GradleDaemon`) and Homebrew as Ruby; `gradle.wrapper`, `npm.npx`, `bun.cache`, `pubcache.hosted`, `homebrew.cache` and the remaining shipped rules without a native command have no name gate at all. The affected gated rules are `gradle.version_cache`, `npm.cacache` and `pnpm.store`; `uv.cache` runs a native binary and is seen. A missed interpreter can delete a cache while its owner is using it, which can break an in-flight build or leave a cache that has to be re-downloaded. For these gated rules it does not create a path into the red list: every delete still passes `realGuard`, and their targets are rule-owned cache leaves, not user-data directories. Mitigation is partial: `busyProcesses: ["java"]` blocks Gradle and `["node"]` blocks pnpm, but naming `node` or `npm` does not catch npm/npx on macOS/Linux, and the shipped rules add no interpreter names because that over-blocks every Java or Node process machine-wide. A command-line-aware detector is feasible but incomplete: `ps -Ao args=` shows `GradleDaemon`, and Windows CIM shows `node.exe … npm-cli.js`, while the POSIX npm/npx title hides the script from both listings. It would add a second cross-platform parser, remain heuristic for wrapped and daemonised tools, and have to fail closed when command lines are unavailable, which would disable the gated rules (not the 22 shipped rules with no name gate). Decision: keep the ceiling, keep the name gate fail-closed when the listing itself fails (entry 110), and leave interpreter opt-in to the rule author where the OS reports the interpreter. Re-audited on 2026-10-20 against the shipped rule set. Follow-up in entry 113: a first-token normalization of POSIX titles was tried and reverted because ambient long-lived `npm exec` processes then blocked unrelated npm-cache cleanup; the name-only ceiling remains.

113. Final security-readiness re-audit of the four known ceilings (2026-10-20), with release guidance. (1) TOCTOU: `realGuard` is read again immediately before path-based `rename`/`rm`, but the check and the syscall are separate operations, so a component swapped after the second check can still be followed. Severity: high impact, low likelihood, high confidence; classification: bounded residual vulnerability, not a demonstrated exploit. The deterministic `moveToTrash` and `apply` race tests install the swap in the `beforeDelete` hook, before the second check; they prove the refusal path, not the post-check window, and there is no equivalent `purgePath` race test. The exact boundary is `realpathSync`/`lstatSync` followed by `rm`/`rename` by pathname; the secure close on POSIX is a parent-directory descriptor opened with no-follow traversal (`openat`/`openat2`), then descriptor-relative `unlinkat`/`renameat` (Windows would need handle-relative APIs). Node/Bun expose none of those primitives. This does not block release under the documented local-user threat model (the threat model now states that a process which can rewrite the user's cache is outside the guarantee), but it does block any claim that deletion is race-free; if a local process racing the user's cache is in scope, it is a release blocker. (2) Busy process: no name-only change was shipped. A first-token normalization of POSIX `ps` titles was implemented and tested: it turned `npm cache verify` into `npm`, but it also turned ambient long-lived `npm exec` MCP servers into `npm`, making unrelated npm-cache cleanups skip (12 e2e failures in the audit environment). That is exactly the unacceptable false-positive gate, so the change was reverted. Windows npm/npx still appear as `node.exe`, pnpm usually as `node`, and Gradle as `java`; `npm.npx` still has no name gate. Severity: low, likelihood medium, impact medium (cache corruption or a failed in-flight build, not red-list data loss), confidence high; classification: bounded limitation. The only safe direction is command-line matching with narrow per-rule markers, not interpreter names; it is left as future work because it needs a second cross-platform parser and an explicit fail-open/fail-closed policy when command lines are unavailable. (3) ReDoS: a user rule's `match` is compiled and run against a basename in-process. The basename is bounded by filesystem name limits (255 bytes on the tested platforms), and the rule file is local trusted configuration; there is no per-regex timeout, so a pathological pattern can still burn CPU per candidate. A spot check of `(a|a?)+` against a 255-byte name took about 1.7 s in Bun 1.3.13; the runtime's backtracking cap is an implementation detail, not a contract. Severity: low, likelihood low, impact low-to-medium (scan delay, no deletion path), confidence medium; classification: bounded local denial-of-service. Do not load untrusted rule files; no regex-rewriting heuristic was added because it would reject valid patterns without proving safety. (4) Windows junction: `tests/windows-junction.test.ts` runs a source-level probe (not the compiled binary) in a child Bun process with a throwaway `HOME`/`USERPROFILE`; all five scenarios pass on `windows-latest`: recursive apply removes the junction leaf while the target survives, paths through a junction into a red directory and through a clean junction are refused, `moveToTrash` moves the leaf and preserves the target, and `findLargeFiles` does not walk through the junction. Severity if followed would be high, likelihood low, impact high, confidence high for the tested runtime; classification: verified behavior for the current Bun/Windows runtime, observed on an advisory Windows job rather than a merge gate (the job is `continue-on-error`, and branch protection requires only Ubuntu). No broad junction exception or name gate was added. Release recommendation: no blocker for the current local-user threat model; document the TOCTOU boundary, keep the Windows junction test, and only add command-line process detection or descriptor-based deletion as a deliberate cross-platform project, not as a name-only patch.

## Engine location

122. The macOS app never resolves the engine to its own executable, and the candidate list can no longer contain the app's binary at all. `BinaryLocator` used to search four roots, one of them `Bundle.main.executableURL?.deletingLastPathComponent()` — the app's own `Dustless.app/Contents/MacOS` folder — and it accepted the first candidate that merely existed. On the default case-insensitive APFS volume `Contents/MacOS/dustless` IS `Contents/MacOS/Dustless`: measured on this machine, `shasum -a 256` of the two spellings yields one digest, so with the bundled engine missing (interrupted copy, partial download, quarantine, a user deleting the file) the app ran ITSELF as the engine, every child repeated the lookup, and the process count doubled per generation — 511 to 1022 live processes and about 150 windows. ## Rule scope and glob expansion

123. A rule's path scope is checked before it can name a target, and a scope that reaches the direct children of `$HOME` is refused instead of executed. The hole was measured, not reasoned about: `dustless rule add evil.green green "test rule" download "~/*"` was accepted silently, the scan reported `~/.config`, `~/my-project` and `~/keepme` as one green finding each, and `apply --yes` deleted all three with `rm -rf` — a permanent delete, not the Trash. `apply`'s refusal list blocked the red paths, `$HOME` itself, the ancestors of `$HOME` and the filesystem root, but not the children of `$HOME`, so the one directory a cache cleaner has no business deleting wholesale was the one the guard did not cover. The check now lives in `patternVerdict` (`src/core/paths.ts`): the pattern is reduced to a shape — a literal prefix, a number of wildcard slots and a literal suffix, with `..` resolved lexically — and the shape is compared with the shape of `$HOME`. Refused: the filesystem root, `$HOME` itself, every ancestor of `$HOME`, and any wildcard slot that can land on a direct child of `$HOME` (`~/*`, `~/*.txt`, `/Users/*`). A path that NAMES one directory below `$HOME` (`~/.cache/x`) is still accepted, because the user asked for that directory by name and the red list already owns the dangerous names (`~/Documents` and the rest); refusing every child would also have broken the shipped "good file" fixture `paths: { all: "~/x" }` that `tests/e2e/outputs.test.ts` validates. A `..` that follows a wildcard is refused outright (the depth it walks is not provable), and a `..` that leaves `$HOME` is refused as an escape. The refusal is enforced in three places, because the three entry points are the three ways a rule reaches a delete: `defect` (`src/core/rules.ts`) so `rule add` exits 1 and writes nothing, `rule validate` so a hand-written `rules.yaml` is named and rejected, and the scan (`candidates` in `src/core/scan.ts`) so a rule that got into the file by hand produces no finding at all and is reported as unscannable with the reason `protected`. One bad path refuses the WHOLE rule at scan time rather than only that path: a rule whose scope contains a protected shape is a rule that asked for too much, and dropping the offending path would silently narrow it. `normalize` deliberately KEEPS such a rule instead of throwing on it: a rules file with one bad rule must not take the other twenty-five rules out of the scan, and the per-rule refusal plus the `protected` reason says the same thing more precisely than a crash would. The scan also drops any resolved path that is the root, `$HOME` or an ancestor of it (`isProtectedPath`, the same real-path canonicalisation `realGuard` uses), so a pattern that expands into one of them cannot become a finding either. Measured on this change: the e2e case drives the compiled binary in a sandbox HOME, writes the rule by hand, and asserts that the scan produces no finding for it, that `apply --yes` deletes nothing and that a canary file in `~/my-project` survives; with the source reverted the same file is 6 of 7 red (the `rule add` refusal, the `rule validate` refusal, the hand-written rule, the `/` and `~` rules, and the shipped project rules), and the old run really did delete the sandbox's `~/my-project`.

124. `resolvePattern` expands a pattern of several segments instead of one, and the shape of the pattern is the contract. The old expander found the first `*`, treated the text before it as the base directory and the text after it as a literal suffix, so `~/*/*/node_modules` built the literal path `$HOME/<child>/*/node_modules`, which never exists: four of the six shipped `project.node_modules` / `project.build` patterns were dead, and the rule was reported as unscannable with the reason `error` and an empty `pathPatterns` list — the tell of a pattern that had silently matched nothing. The expansion is now segment-based: every segment that contains a `*` is a wildcard slot matched against a directory entry name (`*` becomes `[^/]*`, so `*.avd` works as well as `*`), and the literal segments between the wildcards must match exactly. `~/*/*/node_modules` therefore matches `~/a/b/node_modules` and nothing else — not `~/a/node_modules` (one level too shallow), not `~/a/b/c/node_modules` (one level too deep), and not `~/a/other/node_modules` unless `other` is itself one of the wildcard slots. `..` never escapes: it is resolved lexically against the literal prefix, and a `..` after a wildcard is refused rather than guessed at. The expansion is bounded on purpose, because a rule can name a path under `$HOME` and a wildcard can walk a whole tree: `GLOB_LIMITS` (`src/core/paths.ts`) caps a pattern at 12 path segments (a deeper pattern is refused as unsupported at validation time) and the expansion at 20 000 directory entries (hitting the budget returns `EBUDGET`, which the scan reports as an unscannable rule instead of a quietly shortened list). `**` is refused as unsupported rather than silently behaving like a single `*`, because the common meaning of `**` is a recursive walk and this expansion is not one. With the fix the shipped project rules find `node_modules` and `build` at depth 2, 3 and 4 below `$HOME` — the three depths the documentation describes — and the e2e case plants one project at each depth in a sandbox HOME and asserts the six findings.

125. A protected target is reported as unscannable, never as reclaimable. A rule with `paths: { all: "/" }` produced a green finding of 390 594 626 678 bytes (about 364 GiB) for `/`; `paths: { all: "~" }` produced one for `$HOME` and `paths: { all: "~/.." }` one for its parent. The scan sized them by walking the filesystem, added the bytes to `reclaimable`, and the CLI printed "Sẽ xóa 1 mục tự động (364 GB)" — a promise the delete-time refusal in `apply` then broke, because only `apply` knew that `/` was not deletable. The scan now refuses the same set the delete guard refuses (the root, `$HOME`, every ancestor of `$HOME`), so those rules produce no finding, contribute nothing to `totals` or `reclaimable`, and appear in `unscannable` with the new reason `protected`: the information is kept, the number is not. The confirmation summary therefore agrees with what `apply` can actually do, without touching the summary code. The reason joins the `UnscannableReason` union, and `UnscannableSummary` (the type of `ScanReport.unscannableSummary`) gained an OPTIONAL `protected` count so a report written before this change still decodes and so the fixtures in `tests/mcp.test.ts`, `tests/race-delete-apply.test.ts` and `tests/fixtures/windows-junction-probe.ts` still compile without editing files this change does not own. One contract is left open on purpose and is called out here: the macOS app's `UnscannableReason` is a strict `String` enum (`apps/dustless-mac/Sources/DustlessKit/Model/Reports.swift`), so a report that carries `protected` fails to decode until the app adds `case protected = "protected"`, the matching summary field and the three localization strings (`scan.unscannable.reason.protected`). The engine side of that change is complete; the app side is not, and no Swift file was touched by this change.

## Apply and delete safety

126. The delete path re-checks the finding before it deletes it. `verify` was called from exactly one place (`src/core/scan.ts`), and `run` (`src/core/apply.ts`) read only `finding.blocked` and `finding.tier`, so a cache touched between the summary and the delete was deleted anyway and a project that became dirty after the scan was deleted with its uncommitted work still on disk. `revalidate` (`src/core/apply.ts`) now runs after the tier decision and before the confirmation prompt, and returns the reason to skip: the rule's `minAgeDays` is compared with the tree's newest mtime (`treeUsage` in `src/core/space.ts`), the rule's `requireVerify` verdict is re-run (`verify` in `src/core/verify/index.ts`), and the rule's `gitClean` flag is checked (`gitClean` in `src/core/verify/git.ts`). The age check is relative to the scan, not absolute: it fires only when the tree's newest mtime is NEWER than the mtime the scan recorded, which is exactly "touched after the scan" — a cache that was already too young at scan time (demoted to yellow and confirmed by the user) is still deleted, and a cache touched during the confirmation delay is not. A finding whose recorded mtime is 0 has no baseline to compare against and is not age-checked; a real scan always measures a non-zero mtime, so that branch exists only for fabricated findings. When the tree cannot be measured the finding is skipped ("bỏ qua: không đọc được cây thư mục để kiểm tra lại"), never deleted optimistically. The verification result is cached for 30 s per cache version inside `src/core/verify/index.ts` (`gradle_version_unused` walks the whole home directory), so the delete path re-runs the check without adding a second full scan; `git_clean` is never cached, because a repository can become dirty while its cache tree stays untouched — that is the case the re-check exists for. Measured: `tests/apply-safety.test.ts` covers the touched cache (skipped, payload survives), the untouched cache (deleted), the repository that became dirty (skipped, payload survives) and the broken `.git/config` (skipped).

127. The busy-process gate reads command lines, and the tools are detected by their own markers. The old probe listed `ps -Ao comm=`, which on macOS carries the process title truncated to 16 characters: while `npm run sleep` was running the listing read `npm run sleep`, never `npm`, and `processName` reduced that whole title to one name, so a rule declaring `npm` (or a `nativeCommand: npm cache verify`) never matched anything — the gate existed and never fired. `runningCommands` (`src/core/apply.ts`) now lists `ps -Ao args=` and classifies every line into an executable name (the first token, basenamed) plus the tools the command line mentions: `npm`, `npx`, `yarn`, `pnpm` and `gradle`, each with a narrow marker (`npm-cli.js`, `pnpm.cjs`, `yarn.js`, `org.gradle.`, `gradle-wrapper.jar`, a `gradle` path segment). A bare `node` or a bare `java` is not a tool: only a rule that names it in `busyProcesses` can be blocked by it, so no Java or Node process on the machine blocks the whole product. `npm exec …` is classified as `npx`, not `npm`, because those long-lived servers are the exact false positive that made the first-token normalisation revert (entry 113): they own the `_npx` cache, not `_cacache`, and they must not block an unrelated npm-cache cleanup; a rule that names `npx` still sees them. The listing is fetched lazily — only when a rule actually declares a busy process — and only once per run. On Windows the image-name listing (`tasklist`) cannot identify npm, npx, pnpm or Gradle at all, so the engine asks PowerShell for the command lines first (`Get-CimInstance Win32_Process`); if only names are available the listing is marked name-only and a rule that watches one of those tools is skipped rather than deleted, because the condition cannot be verified (entry 110's fail-closed rule, extended from "could not look" to "cannot tell"). The names-only gate for tools the OS reports under their own name (`uv`, `bun`) is unchanged. Measured: `tests/apply-safety.test.ts` drives a fabricated `ps` and asserts that `npm run build` skips the npm rule, that a listing with only `node` does not skip it, that the Gradle daemon under `java` skips the gradle rule, that `node …/pnpm.cjs` skips the pnpm rule, that an ambient `npm exec` server does not skip the npm rule, and that no listing at all keeps the fail-closed skip. Windows has no cheap command line listing: enumerating the command line of every process needs a CIM query that costs seconds, and paying that on every apply is what made the end to end suite time out on the Windows runner, so the listing there carries image names only. The ceiling that follows is recorded rather than papered over: npm, npx, yarn, pnpm and gradle run as node.exe and java.exe on Windows, so the gate cannot see them and their caches are cleaned even when the tool is running. Blocking them instead would leave those five caches uncleanable on Windows, and treating any node or java process as the tool would block every Node and Java project on the machine, so the honest reading is that the gate sees the tools it can see and says so. A listing that cannot be produced at all is still fail closed and skips the finding. The nesting helper compares paths with the separators normalised, because a path may carry the other separator and the platform one is not the only one that reaches it.

128. `freed` is the volume delta and `deletedBytes` is what was deleted; the two are no longer the same number. `freed` was `max(0, freeAfter - freeBefore)`, a delta of free space on the volume that holds `$HOME`, and the CLI printed it as "Đã thu hồi" (reclaimed) — so a deletion on another volume read 0, and any other disk activity during the user's confirmation delay moved the number in both directions. `ApplyReport` (`src/types.ts`) now carries `deletedBytes` next to `freed`: `deletedBytes` is the sum of the bytes of the outcomes whose status is `deleted`, and an outcome that was skipped or failed reports 0 bytes because nothing was deleted (it used to report the size of the item that was left alone). `freed` keeps its meaning — the volume delta — because the e2e contract (`tests/e2e/outputs.test.ts`, `tests/e2e/mcp.test.ts`) and the engine fixture define it that way; what changed is that it is no longer presented as the amount of data removed. The CLI prints "Đã xóa <deletedBytes>" and, on its own line, "Dung lượng trống của volume tăng <freed>"; the macOS app's result card shows the deleted bytes under the existing `deleted` label and the volume delta under `freed` (`ApplyReport` in `apps/dustless-mac/Sources/DustlessKit/Model/Reports.swift`); the MCP `apply` result keeps its six structured keys (the e2e contract asserts the exact key set) and states both numbers in its text. The engine fixture `apply.json` now shows `deletedBytes` 2 580 480 against a volume delta of 1 048 576, so the two numbers are visibly different in the contract the app decodes. `ApplyReport.deletedBytes` is a required field on both sides: the app and the engine ship together, and an older payload now fails to decode loudly instead of half-decoding (see `docs/THREAT-MODEL.md` section 5).

129. Nested paths are counted once. The scan de-duplicated only identical paths, so a rule matching `$HOME/outer` and another matching `$HOME/outer/inner` counted the same bytes twice — measured `reclaimable` of 200 000 for a tree holding 100 000 bytes. The accounting now drops a finding whose path lies inside another accounted finding (`accountedBytes`, `isNested` in `src/core/space.ts`): the claim is decided on the shortest path first, so the parent claims the bytes and the nested child contributes none. It is applied where the numbers are shown — the scan report the CLI prints (`adjustScanAccounting`), the MCP `scan` result, and the deleted bytes of an apply run — and the finding list itself is untouched, so an individual item can still be selected with `--only-file` and deleted on its own. The engine's own `ScanReport.reclaimable` field is still computed by `src/core/scan.ts`, which this change does not touch; the helper it needs is exported for that module, and until it uses it the raw library call still double counts while every consumer of the engine sees the de-duplicated number.

130. `git check-ignore` fails closed. The old verifier read any exit code other than 0 as "not ignored", and `git check-ignore` exits 128 on a fatal error: with a corrupted `.git/config` the verifier answered `{ok: true, note: "path is tracked by git"}` and the finding was treated as verified. `gitIgnored` (`src/core/verify/git.ts`) now tells the three cases apart — exit 1 means the check ran and said no (allowed), exit 0 means the path is ignored (refused), and anything else means the check could not run ("git check-ignore could not verify the path (exit 128)", refused). The note no longer claims a path is "tracked by git" when the check only said it is not ignored. The direction was checked before changing it and stays: `not_in_gitignore` names the condition that must hold for the delete (the path is not ignored by git), and refusing an ignored path is the safe side, because an ignored path is local-only content git cannot restore while a tracked path can be restored from the repository. The verifier is not renamed: the schema that accepts the name (`VERIFY_NAMES` in `src/core/rules.ts`) belongs to the rules module, and renaming the verifier without renaming the schema would leave the schema accepting a name that no longer exists — the exact "syntactically valid but inert" state entry 126 removes.

131. `staleDays` and `gitClean` are enforced instead of accepted and ignored. Both were validated by the rule schema and typed in `src/types.ts`, and nothing in `src/` ever read them, so a user who wrote `staleDays: 30` or `gitClean: true` got no protection at all. Both are enforced now, at the delete gate in `revalidate` (`src/core/apply.ts`): `staleDays` is a hard floor — the tree's newest mtime must be at least that many days old or the finding is skipped — and `gitClean` runs the same `gitClean` check as `requireVerify: git_clean` and skips the finding when the repository is dirty. `minAgeDays` keeps its scan-time meaning (demote to yellow, ask the user) and is additionally re-checked at delete time (entry 121). The schema is unchanged, so no user rule file breaks, and `rule validate` still accepts the fields because they now do something. The scan still reports the rule's own tier for a `staleDays` rule: the floor is a delete-time condition, so a scan's `reclaimable` can include an item the delete will refuse; showing it in the scan needs the scan module (`src/core/scan.ts`), which this change does not touch.

132. The app-install test seam can only narrow. `appDirs` (`src/cli/storage.ts`) returned the `DUSTLESS_APPS_DIRS` override whenever `DUSTLESS_UI_TESTING` was `1`, and that list was passed to `listApps` AND to `uninstall` (`src/core/apps/index.ts`), so in a sandbox HOME `apps --uninstall $HOME/tools/Evil.app --confirm --json` answered `{"status":"trashed"}` where the same command without the seam answered "app not found in inventory" — a test seam that widened the delete scope, against the invariant that every control only ever narrows. The override variable is gone: the shipped binary no longer contains `DUSTLESS_APPS_DIRS`, and the seam is now "the default app directories that are inside the current HOME" (`homeAppDirs` in `src/core/apps/index.ts`), a subset of the defaults. `scopedAppDirs` filters any requested directory list down to that subset and `uninstall` enforces it, so even a direct library caller cannot widen the uninstall scope. `DUSTLESS_UI_TESTING` stays in the binary because the UI harness sets it, but it can only narrow now: it selects a subset of the default directories, never a directory of its own. The UI harness needs no change — its sandbox HOME already makes `~/Applications` the sandbox's own directory, which is exactly what `DUSTLESS_APPS_DIRS` used to point at. The library's default uninstall still moves to the Trash; a permanent delete needs `purge: true` (the CLI's `--purge`), and the macOS app asks for it in a confirmation sheet before it purges. Measured: `tests/apps-seam.test.ts` drives the compiled binary with the seam active and asserts the refusal, that the bundle survives, and that the binary does not carry the seam variable.

## The sudoers rule on macOS, verified

133. The sudoers validator now checks a POSITIVE character set and checks the rule that is about to be written, and the net rule is built through the same allowlist as the AWDL rule. The previous validator refused a list of bad characters — `\0`, a newline, a carriage return, `; | & $ > < ( ) { } [ ] * ? ! # \ ' " ` `,` — which left three holes. A TAB was not on that list and is not whitespace-quoted: `sudoersArg` only quoted a value that contained a space, so a network service whose name held a tab reached the rule text unquoted, where sudo reads a tab as an argument separator. A control character that is neither NUL, a newline nor a carriage return was accepted the same way. And `sudoersRule` did not check the text it was about to write: it deleted the quoted regions from the command and tested what was left, so a command that carried a forbidden character INSIDE a quoted region passed. The validator now works the other way round. A value that reaches a rule must be made of letters, digits and `. _ : @ / + = % ~ -`, or of those plus a single space, which is quoted; anything else — every control character including the tab, every shell metacharacter, every sudoers metacharacter — is refused. The rule itself is then matched against the grammar `<account> ALL=(root) NOPASSWD: <command>[, <command>]*`, where a command is a sequence of bare words and quoted words, so the quoted regions are part of the checked text and a forbidden character hidden inside quotes is refused. An empty command list is refused as well: it used to produce a rule that granted nothing but was still written. The net rule now also goes through `sudoersPath`: the executable of every step must be one of `/usr/sbin/networksetup`, `/usr/sbin/ipconfig` and `/usr/sbin/arp`. The steps themselves always came from that fixed table, so this is a second lock on a value that was already constant, and it is the same lock the AWDL rule has. Measured: `tests/sudoers-rule.test.ts` refuses a tab in a service name, every control character, every shell metacharacter, a forbidden character inside a quoted region, a rule that is not one well-formed line and an account name that could inject a second rule, and it pins the exact AWDL and net rule text. Mutation-checked: with the previous validator in place five of those cases are red — the tab, the control characters, the quoted region, the malformed rule and the net allowlist.

134. The macOS app still does not re-check the net rule, and that ceiling is now measured rather than assumed. `AwdlControl.installPrivilege` refuses any payload that is not exactly the rule it expects — the destination path, the two commands, an account name from a plain character set and the rule text itself. `NetControl.installPrivilege` installs whatever the engine prints. The engine is the only control on that path, which is why the engine-side validator is now a positive character set and a whole-line grammar rather than a list of bad characters: with the old validator a command could carry a forbidden character inside a quoted region and still be written. The re-check belongs on the net path too and belongs to the app, which this change does not own. A second ceiling follows from the character set: a network service whose name holds a character outside the safe set — a parenthesis, an apostrophe, a tab — cannot get a rule at all, so the "remember the permission" button refuses to work on such a machine. That is the safe side of the trade and it is what the old validator did too, but it is now the whole answer rather than a partial one.

## The rule scope and the delete

135. The rule scope is enforced at the delete, and a finding that cannot be tied to a rule is refused. The scope of a rule is checked in three places — `defect` when the rule is written, `rule validate` for a hand-written file, and the scan — but the scan is not the only way a finding reaches a delete: `apply` takes a report, and a report can name a rule id that the rule set does not contain, or a rule whose scope is one the scan would have refused. The delete path therefore re-derives the scope of the rule that produced the finding (`patternsVerdict` over `pathsForRule`) and refuses the finding with the reason `protected` when the scope is not acceptable, and it refuses a finding whose rule id is not in the rule set at all, because there is then no rule that says what the finding may authorise and every rule-derived check — the age floor, `requireVerify`, `gitClean` — would silently not run. The order matters: the tier decision comes first, so a finding nobody selected is still reported as `not_selected` rather than as a rule problem, and the process listing is only paid for by a finding that is about to be deleted. Measured: `tests/rule-scope-apply.test.ts` writes the broad rule by hand, drives `apply` and asserts that the outcome is `failed` with the reason `protected`, that `deletedBytes` is zero and that the payload survives; the same file asserts that a rule id that is not in the rule set is skipped and never deleted, and that a rule with no busy process never lists the process table. Mutation-checked: with the previous `apply` in place the first two cases are red — the broad rule was deleted and the unknown rule was deleted too.

136. The delete-time verification no longer reuses a verdict the scan computed. `verify` caches the `gradle_version_unused` verdict for thirty seconds per cache version, because that check walks the whole home directory, and the delete path called the same function and could be served the scan's answer. In the command line the scan and the delete are two processes, so the cache was empty and the check really ran again; in the MCP server, and in any library caller that scans and then applies in one process, the cache was warm and the delete trusted a verdict that could be minutes or seconds out of date. A project that started using the cached Gradle version between the scan and the delete was not seen, and its cache was deleted. The delete path now asks for a fresh verdict (`verify` with `fresh`), which skips the cache READ but still writes the result, so the other findings of the same version in the same run reuse the fresh answer and the home directory is walked once per version, not once per finding. `git_clean` and `not_in_gitignore` were never cached and are unchanged. Measured: `tests/e2e/verify-fresh.test.ts` drives the compiled binary as an MCP server in a sandbox home, scans, then plants a project that uses the cached Gradle version, then applies; the finding is reported as not deleted with the cause `gradle_used` and the cache survives. Mutation-checked: with the cache read restored the same case is red and the cache is deleted.

## macOS paths

137. The red list names the places macOS keeps real user data in, and `$HOME` is recognised whatever case it is spelled in. The list is the permanent blocklist, and on macOS it missed four families: the Trash, which is the user's own undo; iCloud Drive, in the two spellings macOS uses (`~/Library/Mobile Documents` and `com~apple~CloudDocs`); Apple's own application data, where only four bundle identifiers were blocked and every other `com.apple.*` directory was not; and a Time Machine local snapshot. The Apple pattern was also the only pattern in the list without the case-insensitive flag, and the default macOS volume IS case-insensitive, so `~/library/application support/com.apple.photos` was the same directory as the capitalised spelling and was not red. The patterns are now matched case-insensitively and cover the four families. A third-party bundle identifier is deliberately not red, because the app uninstaller removes exactly those leftovers and the user asked for that. The second half is the identity of `$HOME`: `realpath` on macOS resolves symlinks but keeps the case it was given, so a path could name `$HOME` or one of its ancestors in a different case and step past the guard that refuses the root, `$HOME` and its ancestors. The comparison is now case-folded on the platforms whose filesystems are case-insensitive, in the delete gate and in the MCP guard alike. Measured: `tests/macos-paths.test.ts` asserts the four families are red, that the case variants are red, that a third-party bundle identifier and an ordinary cache are not, that `$HOME` and its ancestors are recognised in any case, that the real-path guard refuses `$HOME` spelled in another case, and that a firmlink (`/tmp` is `/private/tmp`) is not mistaken for a symlink.

138. A rule cannot name the root of a mounted volume, and the rules file only moves when `XDG_CONFIG_HOME` is absolute. On macOS `/Volumes` is where every disk, disk image and network share is mounted, and a rule whose scope is a volume root is a rule that asks to empty a whole disk — the same shape as the `~/*` rule that entry 123 refused, so it is refused the same way: `/Volumes`, `/Volumes/*` and `/Volumes/<name>` are protected scopes, while `/Volumes/<name>/cache` is not. `XDG_CONFIG_HOME` is honoured on macOS as on every other platform, but only when it is absolute: a relative value is not a directory, it is a path relative to wherever the engine happens to run, and a rules file that follows the working directory is a rules file an attacker can place by moving the shell. A relative or empty value is ignored and `~/.config/dustless/rules.yaml` is used. Measured: `tests/macos-paths.test.ts` asserts the volume scopes and the config directory behaviour.

## Screen truth and the app's own words

139. The app renders the engine's data in the user's language and never the engine's prose. The shipped rules in `src/core/default-rules.yaml` are not one language: measured on the 26 bundled rules, 14 carry a Vietnamese `desc` and 12 an English one, and the app printed that `desc` verbatim, so one list showed "Gradle cache của version không project nào dùng" next to "npm cache tarball" in an English or Chinese interface while the reason code underneath was correctly translated. The rule id is the stable key, so the app now owns a table of rule id to localized description (`rule.<id>` in `Model/Localization.swift`, in vi, en and zh) and renders that; the engine's own `desc` is used only for a rule the user wrote themselves, because their text is theirs and must be shown unchanged (the fallback is the localized "A rule you added yourself"). The reason itself is the engine's reason code rendered by `ReasonText`, never the code and never the engine's sentence, and every code the engine can send now has a sentence in all three languages: `not_determinable`, `not_executable` and `engine_unavailable` were missing, so `ReasonText.text` returned the literal `reason.not_determinable` and the screen showed a code. A finding that is locked and carries no reason now shows the tier's own explanation, so a locked item always says why it cannot be deleted.

140. A count in a sentence is a phrase, and the phrase is built where the number is known. The Cleanup footer said "1 locked items excluded" because the templates took a bare number and appended a plural noun. Every count that reaches a sentence now goes through `AppSettings.count`, which picks the one form or the many form (`itemOne`/`itemMany` and the `count*One`/`count*Many` pairs for paths, files, apps, processes, rules, locked items and related files), and the sentence templates take that phrase in `{count}`. `{n}` keeps its meaning everywhere: a number. The same change fixed "1 processes", "1 files", "1 apps", "1 related files", "These 1 paths will be permanently deleted", "Deleting 1 items" and "1 rules could not be scanned". The rule that counts a thing and the noun that names it are now the same word in the Overview, the Cleanup, the menu bar, the storage panel and the confirmation sheets.

141. The engine error is one message, with the sentence first and the searched paths underneath. The message was printed in orange monospace with a two-line limit and a tail truncation, so it ended mid-sentence: "Build it with `bun run build`, then run `bun run bundle:mac` to…", and on the Network panel the same text appeared twice because the network read and the AirDrop read failed for the same reason and both reported it. `EngineErrorMessage` now renders the sentence in the normal error style, the searched paths one per line in a quieter monospace, and the build hint under them, and it never truncates: the `errNotFound` template still carries the `{list}` so the rendered message names every path the engine looked at, and the app splits it into the sentence and the paths itself. The Network panel reports an error once: the AirDrop error is hidden when it is the same message as the network read. The menu bar popover shows the sentence and the hint but not the path list, which would make a 320-point popover ten lines taller for no gain; the full message is in its tooltip.

142. The Overview is a bounded dashboard, not a scrolling page, and it says what it measured. The content was a `ScrollView` inside `PanelScaffold`, so the tier strip, the findings and the call to action were invisible off screen and the screen was mostly empty in the window. The content is now `OverviewContent`, laid out as a two-column dashboard (the largest findings on the left, the coverage and the module state on the right) with no scroll view, so the whole screen draws and can be judged. The hero shows the reclaimable total the engine measured, not a count-up animation frame: the animation made the number disagree with every other screen for the first 450 milliseconds, and the off-screen render caught it at 349 KB against the 3.5 MB the engine reported. The reclaimable total and the selection are two different, separately labelled numbers ("Reclaimable" and "Selected"), the tier cards show the bytes per tier and not the item counts the sidebar already shows, and the primary action ("Review & Delete…", "Scan now", "Choose items to clean…") lives in the header so that expanding a disclosure can never push it off the screen. The unscannable notice lists each reason in plain language on its own line, with the count next to it, and the disclosure names the rules that carry it.

143. The selection is explicit, and a rescan says what it changed. A rescan used to reset the selection to the engine's `initialSelection`, which is always empty, so the user's choice silently disappeared and a scan that returned far more findings could change what the delete button was about to delete without saying so. `ScanStore.rescan` now keeps the paths that still exist, and when any of them disappeared the Cleanup footer says how many of the previous selection are still listed. The first scan still starts with an empty selection: nothing is selected until the user selects it.

144. The privileged network rule is checked before it is installed, the way the AirDrop rule already was. `NetControl.installPrivilege` took the rule the engine printed and installed it as root without comparing it with anything. It now refuses anything but the rule the app expects: the destination is `/etc/sudoers.d/dustless-net`, the four commands are exactly the `networksetup -setdnsservers`, `ipconfig set`, `arp -d -a` and `networksetup -setMTU` forms the engine produces, the account name is plain, and the rule text is exactly the line those commands make. A service name with a space is accepted only in the quoted form the engine emits, and the characters that could change a sudoers rule's meaning (a comma, a `#`, a backslash, a quote, whitespace outside the quotes) are refused. A rule that does not match is not installed and the user is told the engine asked for something the app does not recognise.

145. The AirDrop permission is explained before macOS asks for the password. The Network panel already put a visible line next to its "remember this authorization" button; the AirDrop button had only its own label, so the user met an administrator password prompt with no idea what it was for. The AirDrop button in the Network panel, in the menu bar and in Settings now explains what the permission does, that it writes a rule to `/etc/sudoers.d/dustless-awdl`, that macOS asks for the administrator password once, and that it can be removed again from Settings, and a confirmation carries that explanation before the prompt appears.

146. The app reads the engine's output from a file, not from a pipe. The launcher read the engine through a pipe, and every child inherited the descriptors the app had open, so two overlapping launches could hold each other's pipe open and the unconditional deadline reported `.timedOut` for an engine that had already answered. The launcher now gives the child a file for its output and stderr and reads them after the process ends, so no child can keep another child's output open. The schema version is also checked before the payload is decoded, not only when decoding fails: a well-formed report from an engine that speaks a newer major version used to decode by shape and be shown as if it had been understood.

147. A destructive control reads as destructive, and the advanced features live in an advanced area. `Button(role: .destructive)` without a tint does not paint red on macOS, so the storage rows' "Uninstall" and "Move to Trash" were rendered in the default colour while the app's own `DestructiveButton` was red; both now carry the same red tint. The operations that have little to do with clearing caches are still there but moved down: the DNS, ARP and MTU operations sit in a collapsed "Advanced network operations" area that says what they do and that they ask for a password, and the application inventory moved out of the Storage panel's own tab into a collapsed "Advanced" area with its own search field. Every network operation, safe or advanced, now asks first and names the operation and its effect. /System/Volumes/Data, and a persistent failure still fails the run unchanged. The rerun of the failed

150. The unscannable notice gives its rows room, because Vietnamese and Chinese fuse them otherwise. The

151. The dmg step frees the diskimage slots the boot image spends on simulator runtimes, because the
helper's table was the constraint. The failing runners reported "No space left on device" from
`hdiutil create` with 96 Gi free on both the system and the Data volume, and the diagnostic run
measured what actually sits behind the error: `hdiutil info` lists 15 attached images, nearly all of
them the simulator runtime cryptexes the runner boots with (AppleTV, watchOS, iOS), and even a
5 MB scratch create with no `-srcfolder` failed — so no new image could get a slot, whatever its
size, while the same fleet handed out runners that created the image on the first try. The step
therefore detaches the simulator runtime images (passwordless sudo, `hdiutil detach -force`) before
the create, prints the attached count after the cleanup, and leaves the create itself unchanged:
healthy runners lose nothing, sick ones get the slots the image needs. Notarising nothing here: the
depth is one disk and the work is throwaway, and the images are detached again by the next runner
reimage anyway.

152. The dmg build no longer consults Disk Arbitration, and the CI mount check mounts directly.
The diagnostic run's numbers: after the twelve simulator runtime cryptexes were detached (see 151)
the attached count fell from 15 to 3, and a 5 MB scratch create that had been malformed until then
(its `-format` flag without `-fs` printed usage and ran nothing) succeeded in one second on a runner
that had failed every image all evening, so the table was not the only broken organ. The create the
release needs carries `-srcfolder`, and that form copies through a volume it mounts internally; every
attempt still died with "No space left on device" at that mount, while a mount-free create ran
cleanly, so the mount machinery itself — Disk Arbitration — is what the sick runners lose. The build
now never consults it: an explicit-size HFS+ image is created (mount-free), attached with
`-nomount`, mounted by `mount(2)`, filled with `ditto` plus the Applications link, unmounted with
`umount`, detached, converted to UDZO, verified by checksum and `imageinfo`, then mounted read-only
the same way to prove the app, the Applications link, the signature and the engine's version. Every
claim the old create proved is proved still — the engine identity by hash against the bundle, the
signature deep, the version, the link target — and the size check now reads the deliberately asked
size instead of whatever a srcfolder-sizing pass decided. The CI step that had mounted through the
same machinery was rewritten on the same primitives, so "the image must hold the app" is still a
mount-proven statement, made without the organ that was broken. On healthy runners the recipe runs
unchanged in meaning, and the day's evidence says the sick runners can now build the same image.

153. The rules engine refuses the system roots the uninstall path already refuses.
An audit session probing the scope guards with the engine's own functions found what the
anchored-scope check cannot see: an absolute custom rule scoped to /Library, /System, /usr, /bin,
/sbin or /Applications loads clean, scans, and is deletable with `apply --yes`, because the
protected checks only know the filesystem root, `$HOME` and `/Volumes`, while the uninstall path
carries its own `DENY_PATHS` for exactly those roots. The probe that proved it is pure: for
`/Users/<me>/../Library`, `patternVerdict` answered `{ok:true}` and `realGuard` returned `{real}`
— every guard stage green on a path an author never intended as cache territory. The fix moves the
constant into paths.ts as `SYSTEM_ROOTS` and checks it in two places: `patternVerdict` refuses a
fixed prefix (the segments before any wildcard) that sits under a system root, and
`isProtectedReal` refuses a resolved real path there too, so both the load-time verdict and the
delete-time realpath check catch it, including the `..`-composed forms. `/Users/<someone-else>/…`
is refused the same way on macOS (the second segment under `/Users` must be the current user's).
`/opt/homebrew` deliberately stays open — the bundled homebrew rule depends on it. The new checks
read POSIX paths: they run on mac and linux, while windows keeps the checks it already had; the
windows runner's own rules are `LOCALAPPDATA`-shaped and `/Library`-style roots are not windows
territory. Nothing else
changes: deep `$HOME`-anchored rules sail through, and the unmeasured-scope window for
wildcard-first patterns remains guarded per resolved candidate. Scan reports the refusal as
`protected`, both to the CLI text and the app's reason table.

154. Size accounting counts a hardlinked inode once per tree.
The same audit session measured the double count directly: three pathnames reaching two inodes of
4096 bytes reported 12288 for `treeUsage` while the real block cost is 8192, and deleting one alias
still left the remaining pair double-counted. The walks in scan.ts and space.ts now carry a set of
`dev:ino` identities and skip the size of any file with `nlink > 1` that they have already seen, so
`reclaimable`, the scan totals and `deletedBytes` stop claiming the same content twice, in both the
scan-time walk and the apply-time re-measure. The ceiling keeps its ponytail comment: the set lives
inside one walk, so content aliased across two different findings still counts in each — cross-tree
dedup would need scan-global state for a case no shipped rule produces.

155. The MCP text reports the freed delta as what it measures.
`freed` is a whole-volume `statfs` delta, so a busy volume can credit the run with bytes another
process released: the probe that measured it printed 311 GB "freed" while the run deleted nothing
(the formula is asserted in the tests, so the number itself stays as documented). The MCP apply
summary said "Freed X of volume space", which attributes the delta to the run; it now reads "Volume
free space rose by X", which is the statement the measurement actually supports. The CLI's
Vietnamese text already said the volume rose, and the JSON fields are untouched, so only the one
English sentence changed.

156. The app refuses a second destructive press instead of racing it.
The audit session replayed the destructive walks end to end and found the re-entrancy
pattern uneven in three places. `ScanStore.clean()` had no guard of its own while its
sibling `rescan()` always did — a second press of the review sheet's delete button
before the first apply reached its first mutation would hand the engine two `apply`
runs. `StorageControl.uninstall` and `trash` flipped their in-flight flags without
checking them, so a second click inside the confirm sheet ran a second engine call in
parallel. And both storage sheets bound a destructive confirm button to Return with
`keyboardShortcut(.defaultAction)`, while the main confirm sheet deliberately gives
its destructive button no shortcut — a stray Enter would move a large file to the
trash with zero modifier held. The guards now mirror the house pattern everywhere:
`clean()` refuses any phase but ready, the storage actions refuse while busy, and the
two shortcuts are dropped, with the source sweep that used to exempt the storage
sheets inverted into "no sheet answers Return with a destructive action". The keyboard
contracts belong to SourceContractTests by precedent, so the three new contracts live
there; the guards themselves remain ordinary one-line refusals.

157. Signing credentials are torn down on every path the signing step can end.
The packaging audit traced every call site of the cleanups and found them wired only
to failure exits: `importCertificate` and `resolveSigning` restore the keychain list
and remove the throwaway keychain on their own errors, while the success path — the
one every actual release run takes — left the Developer ID signing identity and the
keychain search-list append in place for the rest of the job, and `resolveNotaryCredentials`
left the 0600 `AuthKey.p8` tempdir behind when submission, stapling or Gatekeeper
rejection failed midway. `signApplication` and the notarisation script now run those
teardowns in `finally` blocks: success, mid-signing failure and mid-notarisation
failure all end with the keychain unlisted and deleted and the key file removed.
The teardowns were idempotent by construction (keychain-list set, `rm -rf`), so no
double-cleanup hazard exists.

158. The dmg workflow detaches under the same privilege that attached it.
The CI mount check attached the image with `sudo hdiutil attach` but detached as the
runner user; a DiskImages2 device registered by a root session is not guaranteed to
be detachable by a non-root caller, and a detached-as-user failure would turn an
all-green check into a false red after every substantive assertion had passed. The
detach now runs under `sudo` to match the attach. The same session reconciled the
packaging docs with the code they describe: the disk image is created at an explicit
size (staged tree plus 96 MiB) and its `imageinfo` size is cross-checked against what
was requested; the pre-rewrite claims (a staged-engine hash step that has since
moved into the filled image, and a refused-if-more-than-twice-as-large rule) were
several commits stale. The docs also now state what `MACOS_NOTARY_PROFILE` really
requires — a profile created by `notarytool store-credentials` on that machine — so a
hosted runner is told to use the API-key or Apple-id trios instead of a creed that can
only ever fail loudly there. The three-attempt `hdiutil create` retry that DECISIONS
149 once described was removed with the DiskArbitration rewrite (152) and it stays
removed deliberately: the mounted-free create needs no slot machinery, the workflow
frees the image slots itself, and a transient create failure now fails the step
loudly on its single attempt rather than papering over a runner that will go on
failing.

159. For rules that declare nothing, the delete path trusts the path it scanned.
The audit's swap probe planted a different tree at a finding's path after the report
was built and then asked the engine to delete the finding: for a rule that declares
none of `staleDays`, `minAgeDays`, `requireVerify` or `gitClean`, the run deleted the
replacement without noticing, because every runtime re-check is opt-in per rule and
the finding's identity is the path string the scan recorded. The window is exactly
the no-declaration case: a rule that does declare an age floor is protected by the
revalidate contract of 126 — the tree's fresh mtime is measured at delete time and a
newer baseline than the scan's is refused — so a planted replacement is caught as
long as its fresh mtime betrays it; a replacement whose mtimes were restored matches
nothing short of content identity, which the finding format does not carry. The line
this version holds: reopening every tree on every delete would charge the default
path the walk that only rules claiming age sensitivity pay now. The upgrade paths
are a cheap per-finding lstat compare against the scan-time snapshot (same
newer-than-scan semantics 126 defines, no schema change) or a content fingerprint in
the finding itself (schema change).

160. The busy gate refuses what the rule declares, and nothing beyond it.
The audit's fixture session saw the gate behave exactly as declared: a `sleep`
process named in the rule's `busyProcesses` held the tree and dispose refused with
the busy reason until the process exited; nothing checked any other holder. A
process that writes into the tree while it is deleted is a real window when no
declared name matches, and the audit looked at the two general gates it could carry:
an `lsof` sweep is a full-process fd walk per finding, and a post-delete audit only
reports damage after it is done. Both pay their cost on every run to guard the
unusual case, so the engine keeps the declared-contract gate with its fail-closed
corner intact (a system where process listings cannot be read refuses rather than
deletes, which the test "no process listing at all keeps the fail-closed behaviour"
locks). The honest answer to an author who cannot name the interfering processes is
the tier and confirmation contract, not a heuristic sweep.

161. Size accounting reads logical byte lengths, not allocated blocks.
`treeUsage` and the scan walk sum `stat.size`, so `reclaimable`, the scan totals and
`deletedBytes` all carry logical lengths, and the freed delta compares volumes whose
frees are paid in blocks. A sparse file reports its full logical length while the
volume gives back only its allocated blocks on removal, so a sparse-heavy tree
over-promises reclaimable and the two numbers drift apart. The audit kept it
deliberately: the shipped rules' territory — caches — is dense in practice, a
regular file's logical size is exactly what a `rm`-based contract reads, and one
consistent number across scan and apply is worth more to every consumer than a
second, sparser truth. The upgrade path is a one-line change in the two sum sites
(`st_blocks × 512` instead of `size`) with the fixtures recalculated; it changes the
meaning of every consumer at once, so it wants its own decision, not a ride-along.
## Quick control center (2026-10 redesign)

A scan never pre-selects anything (entry 71), so `menubar.quickClean` cannot delete on its own: `selectQuickClean` (`ScanStore`) unions the ids of `ScanReport.quickCleanFindings()` — green tier AND engine-deletable, the exact set `selectAll(in: .safe)` unions — then opens the Cleanup module and raises the same `ConfirmDeleteSheet` the manual review flow raises.
